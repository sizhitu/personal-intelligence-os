# 案例库验证协议

## 验证目标
案例库不是用来证明模型“总能解释过去”，而是测试系统在信息不完整时能否形成可审计、稳健且不过度自信的决策。

## 必做测试
1. **时间截面测试**：冻结事件发生时可得信息；分析者不得看到后续结果（盲测）。
2. **模型路由测试**：记录候选模型、被选模型及排除理由；评审是否遗漏关键机制。
3. **因素覆盖测试**：由独立评审检查是否遗漏流动性、杠杆、政策、估值、盈利、竞争与二阶效应。
4. **权重合理性测试**：权重理由须映射到目标、硬约束、证据和模型，不可只给数字。
5. **雷达图测试**：雷达图只表达因素重要性；禁止把权重图冒充方案表现图。
6. **敏感性测试**：各普通权重相对扰动 ±20% 后归一化；报告建议是否逆转、关键阈值和脆弱性。
7. **双视角测试**：持仓者和获益方必须分别说明目标、约束、成本、风险；获益方需计入借券/融资/挤压成本。
8. **反证测试**：每案至少列一个能推翻主结论的观察指标和一个历史反例。
9. **结果偏差测试**：评估决策时只看当时信息；事后结果单独评分。
10. **校准测试**：记录概率预测与实际结果，使用 Brier score/校准曲线；样本不足时不声称统计显著。
11. **版本测试**：任何模型、因素或权重规则变更都需版本号、理由、影响案例和回归测试。
12. **可复现测试**：案例数据 JSON schema 校验、来源 URL 可访问性抽检、内容哈希和 commit 固化。

## 评分维度（0–5）
- 事实准确性
- 时间截面纪律
- 模型路由适配
- 因素覆盖
- 权重可解释性
- 证据可信度
- 反证质量
- 方案可执行性
- 稳健性/敏感性
- 事后校准质量

评分不能简单相加后宣称模型优劣；先报告分项、缺陷和样本量。

## 反方角色
每个案例都由“红队”提出至少两条反驳：
- 当前主结论最可能错在哪里？
- 哪个未观测变量会改变结果？
- 这是否只是幸存者偏差/叙事拟合？
- 获益方是否真的能在当时执行，而非事后看起来获益？

## 自动化边界
v0.1 是人工整理的基准样本，不是量化回测，也不是交易策略。没有逐日价格、财报预期快照、期权/借券成本和当时可用新闻档案时，不得宣称完成历史交易回测。
